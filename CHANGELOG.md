# Changelog

The notable changes to Hieu UI Lab, newest first. The project is at version 0.1.0 and has no tagged releases, so entries are grouped by the date a pull request merged, with its number. Work that is not merged yet is listed under Unreleased.

## Unreleased

- shadcn CLI install workflow: no Hieu UI Lab CLI was built, because the official CLI already does what one would have to do, and the docs page [Install with the shadcn CLI](/docs/shadcn-registry) now says so, lists the commands that were run, shows how to point the `@hieuuilab` namespace at another address, and tabulates what the CLI prints when an install fails. `pnpm registry:failure-test` checks that, with the real CLI against a local server of crafted answers: invalid names, missing files and bad statuses, malformed items, paths that leave the project, dependencies that cannot be installed, and an unset registry variable. It passed for shadcn 4.22.1 with pnpm and with npm on Node.js 22.22.3, and the install workflow runs it too. It found that `--dry-run` does not apply the path check of the real command, and that an empty file list and a file without content exit with 0 and install nothing. The helpers shared by the two scripts moved to `scripts/lib/registry-harness.ts`, and `src/registry/shadcn/schemas.test.ts` tests the two schema validators on malformed items.
- shadcn CLI: Kbd is published as a shadcn registry item, so `shadcn add` can install it by URL or through the `@hieuuilab` namespace. `public/r/registry.json` and `public/r/kbd.json` are generated from the registry entry and its source file by `pnpm registry:build`, and `pnpm registry:check` (also part of `pnpm test` and a CI step) fails when they drift. The generator checks that every referenced file exists, that declared and imported packages match, that names are unique and do not collide with a shadcn item by accident, and that the item passes both the JSON Schema shadcn publishes and the schema inside the CLI package; it refuses components that need this site's own tokens or utilities. `pnpm registry:install-test` installs the item into a clean project made by `shadcn init`, builds it, opens it in a browser, and exercises the conflict cases; it passed for shadcn 4.22.1 with pnpm and with npm on Node.js 22.22.3, and no other version, runner, framework, or public URL was tested. A new docs page, [Install with the shadcn CLI](/docs/shadcn-registry), states that, and what the CLI does with a file you already have. The installation page and one engineering note no longer say there is no registry file. Added the `shadcn` (exact version) and `ajv` development packages and a weekly workflow, `registry-install.yml`.
- Three.js scene: `/labs/3d/three-scene` is an interactive scene of five solids on a lit grid, added to the existing 3D category. The camera orbits and zooms within limits that keep it above the ground and inside the stage; a plain mouse wheel scrolls the page and Ctrl or ⌘ with the wheel zooms. A solid is selected by clicking it or from a list, six camera buttons and Reset camera give a keyboard route to everything dragging does, and reduced motion removes the camera's inertia and makes Reset camera jump. The scene draws only when something changes, so an idle scene requests no animation frames, and a Renderer stats panel shows the renderer's own counters. Three.js is imported only under `src/lab/three-scene/runtime/`, through one dynamic import, so it is a chunk that only this page downloads, and only in a browser that can create a WebGL2 context. Leaving the page releases the geometries, materials, listeners, and the graphics context in that order. The scene is built from layers (the ground and the solids), which is where building extrusions or terrain would be added; neither is built yet. The WebGL2 check moved to `src/lab/shared/webgl-support.ts` and is shared with the map viewer, and the 3D category and Labs copy no longer say that every 3D experiment avoids a 3D library. `e2e/three-scene.spec.ts` runs the real library. Added the `three` and `@types/three` packages.
- Map viewer: `/labs/maps/maplibre-viewer` is an interactive MapLibre GL JS map of an invented island, with toggleable layers and their status, selectable features and an info panel, a route, a legend, and loading and error states. Its basemap is drawn from data in the repository and makes no network requests; an online basemap is opt-in, configured at build time with the `VITE_MAP_*` variables listed in the new `.env.example`, and loaded only after a click. The map library is imported only when a browser can create a WebGL2 context, and its web worker is handed over with `setWorkerUrl`, without which a production build could not start the map. A new docs page, [Map viewer and basemaps](/docs/map-viewer), records each provider's attribution, usage policy, and key requirements as checked on 2026-10-21. `e2e/maplibre-viewer.spec.ts` runs the real library. Added the `maplibre-gl` and `@types/geojson` packages.
- About page: `/about` now introduces the author as a frontend engineer focused on React, TypeScript, reusable UI systems, and practical engineering. Skills are grouped into eight engineering domains, each citing source files and linking to the projects and notes that show it, and learning goals are listed separately as goals, not achievements. The content is one typed profile, `src/content/profile.ts`, checked in `pnpm test` by `validateProfile`: evidence files, anchors, project and note slugs, and npm packages must exist, a goal's package must not be installed yet, and wording such as expert or production-proven is rejected. The GitHub links are shown, and a CV or an email appears only when one is added to the profile. The footer's Contact group reads the same links. The lab inventory, planned entries, and tech stack moved below the profile. The heading is now About Hieu.
- Engineering notes: `/notes` is a technical learning journal of Markdown articles in `src/notes/content/`, with tags (`/notes?tag=react`), article pages with a table of contents, an evidence list, and related articles. Every article follows one template: context, constraints, alternatives, an implementation example, verification with what it does not verify, trade-offs, and references. `pnpm notes:check` validates them against the repository, and CI runs it: a code block must be an excerpt of the file it names or be labelled hypothetical, commands must be the repository's own scripts, and the evidence files must exist. Four articles are new (component APIs, strict TypeScript, React Hook Form with Zod, and registry validation), and the four earlier notes moved to the same format. The guide is `src/notes/README.md`.
- The Markdown rules shared by the docs and the notes moved to `src/docs/markdown-rules.ts`. Showcase evidence can now cite `tsconfig.json` and `tsconfig.app.json`.
- Documentation system: these pages are Markdown files in `src/docs/content/`, with nested sidebar navigation, breadcrumbs, a table of contents, highlighted code blocks with copy buttons, and a 404 that suggests the closest pages. Props tables, design tokens, and live examples are generated from the registry and the stylesheet instead of being copied. `pnpm docs:check` validates internal links, `#heading` anchors, repository paths, and the imports in code samples, and CI runs it. The four hand-written docs pages are replaced, and `/docs/architecture` moved to `/docs/project-structure` and redirects.
- Code blocks highlight TypeScript, JSON, and CSS as well as TSX. Code blocks, props tables, and documentation tables can be scrolled with the keyboard while they overflow.
- Added the `marked` package, which parses the documentation Markdown.
- Templates: three example apps at `/templates` (admin dashboard, operations monitoring, and data management workspace), each built only from registry blocks with invented data.
- Project showcase at `/projects`: public projects whose claims cite files in the repository, checked by a validator.
