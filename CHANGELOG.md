The notable changes to Hieu UI Lab, newest first. The project is at version 0.1.0, which is prepared but not tagged: no release exists, so the version section has no date yet. Below it, entries are grouped by the day a pull request merged, with its number. Unreleased holds changes made after the version section was written.

## 0.1.0

### What is in it

- A registry of 49 entries, 30 components and 19 blocks, each with a live example, copyable source, a props table generated from typed metadata, install steps that follow registry dependencies, and a validator that checks the metadata against the source. One more entry, Combobox, is planned and says so. The catalog searches, filters, and sorts with the state in the URL.
- Eight page blocks (dashboard, monitoring, CRUD, search and filter toolbar, profile settings, notification center, sign-in, onboarding) and three example apps at `/templates`, built only from blocks and invented data.
- A playground at `/playground` and on entry pages, with typed controls, light and dark previews, preview widths, and copyable code. It runs only examples from an allowlist; no code is compiled or evaluated.
- Design tokens for light and dark themes with contrast tests, a theme menu that follows the system, and no flash of the wrong theme.
- Documentation at `/docs` from Markdown that a validator checks against the repository, engineering notes at `/notes` and a project showcase at `/projects` whose claims cite files, and an About page built from a typed, validated profile.
- Four lab experiments: a map projection explorer, a WebGL2 scene, a MapLibre GL JS map viewer with a bundled basemap, and a Three.js scene. The two libraries load only on their pages.
- Kbd published as a shadcn registry item, installable with the unmodified shadcn CLI (`pnpm registry:install-test` and `pnpm registry:failure-test`). Nothing is published to npm.
- Checks: ESLint with accessibility rules, strict TypeScript, Vitest, Playwright end-to-end tests with axe scans in both themes, validators for the docs, notes, profile, showcase, and registry, a check of the build output, and a deployment rehearsal against a local server that applies `vercel.json`.
- Not done: the site is not deployed, no map provider was used, only Chromium was tested, and no field performance data exists. See [Known limitations](/docs/known-limitations).

### Changed by the release audit

- Moving between registry entries in the sidebar kept the previous entry's playground controls and code tab: `/components/button` with a Variant set, then Badge, showed Button's label and variant on Badge. The detail page is now keyed by entry. `src/pages/registry-detail-page.test.tsx` and `e2e/playground.spec.ts` follow that move.
- A page whose script could not be loaded (a tab opened before a deployment asks for a file that is gone) showed an empty page body, not the error page, on every lazy route that has no loader of its own (About, Playground, the Templates, Projects, Notes, and Labs indexes, and the Labs category pages). React Router 8 drops the error of an object-form `lazy: { Component }` there. The routes use the function form now, and `e2e/route-errors.spec.ts` and `src/router/route-errors.test.tsx` fail if that changes. The error page also has a test for a page that throws while it renders and for a failing site shell.
- An entry's Installation step 1 listed only its own setup requirements, so Error state did not mention the cn helper and the state utilities that Button and Empty state bring. The install plan now merges the requirements of everything the entry copies (`src/registry/install.ts`, `src/registry/install.test.ts` for every entry).
- Each template's file list now includes the `@/registry` helpers it imports (`demo-controls`, `mock-delay`), and a test fails when an import is missing from the list. A failed template preview no longer stays failed when you move to another template: the demo error boundaries are keyed by what they show.
- `Button asChild` with `loading` or `disabled` silently ignored both. The child now gets `aria-busy`, `aria-disabled`, and `data-disabled`, and its click is cancelled, as a disabled button would not receive it.
- Breaking, before the first version: `StatusBadge`'s `tone="danger"` is now `tone="destructive"`, the word Button, Badge, Alert, and Sparkline already use.
- Accessibility found by widening the axe scan to a page of every kind: the catalog's search field pointed `aria-controls` at a results list that did not exist when nothing matched, and the template view buttons named themselves "Notifications, 4 unread" while showing "Notifications 4", so the name did not contain the visible text (WCAG 2.5.3). The scan covers 32 states in both themes, up from 14.
- The props tables of Error state, Resource list, Data table, and Form were missing props their interfaces declare; `src/registry/props-drift.test.ts` now compares every `<Part>Props` interface with its table.
- The About page's performance goal cited a README sentence that no longer existed, which made `pnpm test` fail on `main`; its wording and evidence now describe `pnpm perf:measure`. The README no longer lists MapLibre as planned, lists every script (a test keeps it complete), and has Contributing and License sections.
- Added the MIT `LICENSE`, the `license`, `description`, `author`, `repository`, and `bugs` fields of `package.json` (the package stays private), `THIRD-PARTY-NOTICES.md` for the packages and fonts in the build, and `CONTRIBUTING.md`. `scripts/lib/release-metadata.test.ts` fails when a runtime dependency is missing from the notices or its license changes.
- `CHANGELOG.md` takes a version section between Unreleased and the dates (`## 0.1.0`, or `## 0.1.0 - 2026-10-27` once tagged), and Unreleased may say "Nothing yet."; the validator and its tests changed to match. The entries that sat under Unreleased are filed under the dates their pull requests merged.
- The deployment commands in the docs use `https://<your-deployment>.vercel.app`: the earlier placeholder was a real address that answers 404, which failed `pnpm deploy:links`, and a copied command would have sent a bypass secret to whoever owns that name. `deploy-verify.yml` sets the secret on the two steps that send it, not on the whole job.
- Three new docs pages: [Release readiness](/docs/release-readiness), [Known limitations](/docs/known-limitations), and [Reproduce the quality checks](/docs/reproducing-checks).

## 2026-10-27

- Deployment preparation (not a deployment: the site is still not deployed, and no run against a real host has happened). `vercel.json` sets the Vite build, the single-page-app fallback that lets a nested URL be refreshed or opened directly (it excludes `/assets/` and paths with a dot, so a missing script is a 404 and not `index.html`), one-year caching for hashed files, and security headers; `src/router/vercel-config.test.ts` compiles it with Vercel's own route compiler (the new `@vercel/routing-utils` development package, exact version) and checks it against every URL the site serves, and a changed rewrite to a bare catch-all fails it. The map viewer now reads its four `VITE_MAP_*` settings by name: it passed `import.meta.env` whole, which makes Vite write every `VITE_` variable of the build into the public bundle, and a canary variable was found in the output before the change and not after. `pnpm dist:check` (also the last step of `pnpm check`, CI, and the Vercel build command) checks the build output: the files the site needs, root-absolute asset paths, no source maps, no stray `VITE_` setting, secret value, or credential-shaped string in it, and a summary of the map settings; each rule has a failing example in `scripts/lib/dist-rules.test.ts`, and `vite.config.ts` now also runs tests under `scripts/`. `pnpm deploy:smoke <address>` makes the HTTP checks of a deployment, `pnpm deploy:serve` serves `dist/` with the rules of `vercel.json` (or as a host that gets the fallback wrong) so the checks can be tried without a host, and `scripts/lib/smoke.test.ts` shows the check failing for each wrong host. `E2E_BASE_URL` points the Playwright tests at an address (`pnpm deploy:e2e`, with `e2e/external-links.spec.ts` for the links that leave the site), `pnpm deploy:links` asks every web address the repository ships whether it still answers (all 33 did on 2026-10-26), and `.github/workflows/deploy-verify.yml` runs these against an address by hand or after a successful Production deployment; it has not run. A new docs page, [Deployment](/docs/deployment), covers local development, environment variables and secrets, the Vercel settings (including `ENABLE_EXPERIMENTAL_COREPACK`, because the lockfile is read as pnpm 9 or 10 and the repository pins pnpm 11), routing, the map provider and its attribution, the verification steps, what has and has not been checked, the limits of the services involved, and a troubleshooting table. `.vercel` is now ignored. It is on the branch `deployment-setup`, which was not merged when 0.1.0 was prepared.

## 2026-10-26

- Performance and responsive (#22): `pnpm perf:measure` (`scripts/perf-measure.ts`) measures a production build in headless Chromium: what a first visit downloads, how it paints, what loading a route and an interaction cost, and what the WebGL pages leave behind when the visitor goes away. It reports ranges across runs, can run two builds side by side, and says what it cannot tell (a real phone, a real network, field data, the GPU); its results go to `perf-results/`, which is not committed. Each registry entry's examples, source text, and playground moved from `meta.ts` into a `content.ts` of its own, loaded where a page shows the entry, so they left the main bundle; `src/registry/entry-graph.test.ts` fails if the metadata imports them or if anything the app loads first reaches a demo. A route change moves focus to the new page's heading (`src/components/site/route-focus.tsx`, `e2e/route-focus.spec.ts`). The loading fallback fills the screen under the header, so a lazy page no longer pushes the footer out (`e2e/layout-shift.spec.ts`, with every script delayed). The catalog search no longer drops characters typed in quick succession, and a 320 pixel check covers every registry entry (`e2e/shell.spec.ts`, `e2e/catalog.spec.ts`).

A browser without WebGL2 skips the map and 3D specs on a developer's machine and fails them where `CI` is set, and two assertions that passed on either outcome now skip or fail instead. It found five syntax-highlight colors under 4.5:1 on the code background, in Shiki's own themes, which `src/lib/highlight.ts` now replaces, and `src/lib/highlight.test.ts` measures every color the site displays. ## 2026-10-24

- shadcn CLI install workflow (#20): no Hieu UI Lab CLI was built, because the official CLI already does what one would have to do, and the docs page [Install with the shadcn CLI](/docs/shadcn-registry) now says so, lists the commands that were run, shows how to point the `@hieuuilab` namespace at another address, and tabulates what the CLI prints when an install fails. `pnpm registry:failure-test` checks that, with the real CLI against a local server of crafted answers: invalid names, missing files and bad statuses, malformed items, paths that leave the project, dependencies that cannot be installed, and an unset registry variable. It passed for shadcn 4.22.1 with pnpm and with npm on Node.js 22.22.3, and the install workflow runs it too. It found that `--dry-run` does not apply the path check of the real command, and that an empty file list and a file without content exit with 0 and install nothing. ## 2026-10-23

- shadcn CLI (#19): Kbd is published as a shadcn registry item, so `shadcn add` can install it by URL or through the `@hieuuilab` namespace. `public/r/registry.json` and `public/r/kbd.json` are generated from the registry entry and its source file by `pnpm registry:build`, and `pnpm registry:check` (also part of `pnpm test` and a CI step) fails when they drift. The generator checks that every referenced file exists, that declared and imported packages match, that names are unique and do not collide with a shadcn item by accident, and that the item passes both the JSON Schema shadcn publishes and the schema inside the CLI package; it refuses components that need this site's own tokens or utilities. `pnpm registry:install-test` installs the item into a clean project made by `shadcn init`, builds it, opens it in a browser, and exercises the conflict cases; it passed for shadcn 4.22.1 with pnpm and with npm on Node.js 22.22.3, and no other version, runner, framework, or public URL was tested. A new docs page, [Install with the shadcn CLI](/docs/shadcn-registry), states that, and what the CLI does with a file you already have. The installation page and one engineering note no longer say there is no registry file. Added the `shadcn` (exact version) and `ajv` development packages and a weekly workflow, `registry-install.yml`.

## 2026-10-22

- Three.js scene (#18): `/labs/3d/three-scene` is an interactive scene of five solids on a lit grid, added to the existing 3D category. The camera orbits and zooms within limits that keep it above the ground and inside the stage; a plain mouse wheel scrolls the page and Ctrl or ⌘ with the wheel zooms. A solid is selected by clicking it or from a list, six camera buttons and Reset camera give a keyboard route to everything dragging does, and reduced motion removes the camera's inertia and makes Reset camera jump. The scene draws only when something changes, so an idle scene requests no animation frames, and a Renderer stats panel shows the renderer's own counters. Three.js is imported only under `src/lab/three-scene/runtime/`, through one dynamic import, so it is a chunk that only this page downloads, and only in a browser that can create a WebGL2 context. Leaving the page releases the geometries, materials, listeners, and the graphics context in that order. The scene is built from layers (the ground and the solids), which is where building extrusions or terrain would be added; neither is built yet. The WebGL2 check moved to `src/lab/shared/webgl-support.ts` and is shared with the map viewer, and the 3D category and Labs copy no longer say that every 3D experiment avoids a 3D library. `e2e/three-scene.spec.ts` runs the real library. Added the `three` and `@types/three` packages.

## 2026-10-21

- Map viewer (#16, #17): `/labs/maps/maplibre-viewer` is an interactive MapLibre GL JS map of an invented island, with toggleable layers and their status, selectable features and an info panel, a route, a legend, and loading and error states. Its basemap is drawn from data in the repository and makes no network requests; an online basemap is opt-in, configured at build time with the `VITE_MAP_*` variables listed in the new `.env.example`, and loaded only after a click. The map library is imported only when a browser can create a WebGL2 context, and its web worker is handed over with `setWorkerUrl`, without which a production build could not start the map. A new docs page, [Map viewer and basemaps](/docs/map-viewer), records each provider's attribution, usage policy, and key requirements as checked on 2026-10-21. `e2e/maplibre-viewer.spec.ts` runs the real library. Added the `maplibre-gl` and `@types/geojson` packages.
